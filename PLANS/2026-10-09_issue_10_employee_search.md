# Поиск активного сотрудника по ФИО — план реализации

> **Статус:** live E2E MVP пройден после явного GO владельца; создана ровно одна задача и проверен readback. Кандидат готов для draft PR; после открытия остановиться. Личная репетиция владельца и явное одобрение merge/release — отдельные gates.
>
> **Исполнение:** inline в ветке `codex/issue-10-owner-task`; после открытия draft PR дальнейшие действия остановить до отдельного решения владельца.

**Цель:** дать AI read-only поиск активного сотрудника Planfix по части ФИО, чтобы выбирать исполнителя без заранее известного employee ID.

**Архитектура:** один MCP tool `planfix_employee_search` вызывает документированный `POST /user/list` с фильтром 9006 и возвращает только имя/ID кандидатов плюс безопасную пагинацию. Создание задачи, назначение и readback остаются на существующих tools; новый поиск никогда не выбирает сотрудника за пользователя.

**Стек:** Python 3.12+, Pydantic, `httpx`, MCP FastMCP, pytest.

## Scope

Входит: поиск по непустому запросу длиной 1–200 символов; только активные сотрудники; только `id,name,midname,lastname`; фиксированная страница 100 записей с `offset`; `hasMore=true` при полной странице, что требует получить следующую страницу до выбора единственного кандидата.

Не входит: fuzzy ranking, автоматический выбор, task-create wrapper, дополнительная запись в Planfix, plugin/skill, hosted service, Issue #5, рефакторинг REST-клиента.

## Файлы

- `planfix_mcp/client.py` — POST `/user/list` через существующий HTTP helper.
- `planfix_mcp/schemas/employees.py`, `planfix_mcp/tools/employees.py`, `planfix_mcp/server.py` — валидация и регистрация одного read-only MCP tool.
- `scripts/smoke_tools.py`, `scripts/check_swagger_alignment.py` — контракт 59 tools и точная проверка `POST /user/list`.
- `tests/test_employee_search.py`, `tests/test_mcp_contract.py` — точный request body, фильтрация полей, страницы, пустой/слишком длинный запрос, отрицательный offset, API error, malformed response, schema.
- `README.md`, `README_EN.md`, `MANUAL_QA_EXTENDED_TOOLS.md`, `CHANGELOG.md` — новый tool и правило не объявлять уникальность до последней страницы; old 58 tool names остаются неизменны.

## Риски и ограничения

1. API возвращает до 100 записей и не документирует total; полная страница означает «может быть продолжение», поэтому вызывающий запрашивает следующую страницу с `offset + 100` и не выбирает по первой странице.
2. Ответ поиска содержит numeric employee ID. Существующий task-create contract требует prefixed ID `user:<id>`; конвертацию делает вызывающий при подготовке payload, не новый инструмент.
3. Запрос ограничен только полями имени и ID; email, логины и прочие данные сотрудников не запрашиваются.
4. Если после сбора страниц остаётся более одного совпадения, AI уточняет у пользователя и ничего не записывает.

## Шаги

1. Добавить schema `EmployeeSearchInput(query: str[1..200], offset: int >= 0)` и unit tests для trim, пустого/слишком длинного query, отрицательного offset.
2. Добавить `PlanfixClient.list_employees(payload)` как `POST /user/list`; MCP tool отправляет `{"offset": offset, "pageSize": 100, "onlyActive": true, "prefixedId": false, "fields": "id,name,midname,lastname", "filters": [{"type": 9006, "operator": "equal", "value": query}]}`.
3. Вернуть список `users`, `offset`, `pageSize=100`, `hasMore=(len(users) == 100)`; сохранить существующий формат обработки `PlanfixAPIError`.
4. Добавить один tool в smoke contract и `POST /user/list` в Swagger alignment; сохранить имена исходных 58 tools.
5. Обновить русскую/английскую документацию и `Unreleased` changelog: искать по имени, перебирать страницы при 100 результатах, уточнять при нескольких совпадениях, назначать `user:<id>` только после выбора.
6. Запустить целевые тесты, полный pytest, compileall, smoke, Swagger alignment, pip check, wheel build и `git diff --check`; затем передать кандидата root для независимого review/live QA.

## Фактическая проверка кандидата

- Offline: полный pytest — 52 passed; compileall, smoke (59 tools), Swagger alignment (v1.7.8, 54 операции), сборка wheel и `pip check` в отдельном task-specific venv прошли.
- Live STDIO E2E, после явного owner GO: свежий поиск активных сотрудников после уточнения вернул одного кандидата; создана ровно одна задача, без дополнительных create/update writes. Readback подтвердил заголовок и исполнителя.
- В readback Planfix свернул переносы строк описания в пробелы. После нормализации whitespace описание сохранило инструкцию, все три шага и ограничение не связываться с клиентом; потери содержания нет. Production normalizer/helper не добавлялся.
- Срок был задан как «завтра» и разрешён в календарную дату 13 октября 2026 года по часовому поясу аккаунта. Записанная дата `13-10-2026` совпала с датой readback; `hasEndDate=true`, `hasEndTime=false`. ISO-представление полуночи в ответе не означает заданное пользователем время.
- Статус и участники не задавались поручением; фактические значения по умолчанию аккаунта не менялись и не считаются дефектом этого сценария.
- Честное сравнение: официальный Planfix MCP уже завершал тот же бизнес-сценарий (7 вызовов; одно наблюдение 79 секунд без времени подтверждения). Наш кандидат потребовал одно уточнение фамилии из-за неоднозначного имени, тогда как официальный прогон использовал lookup текущего пользователя. Условия и границы измерений различаются: у кандидата было 4 вызова в начальном сценарии, позднее — отдельный read-only diagnostic get; единственное наблюдение 5,3 секунды исключает setup и уточнение владельца. Это не benchmark и не доказывает преимущество по скорости; сравнимое различие только в lookup/confirmation UX.
- После draft PR — личная репетиция владельца; merge/release не выполнять без явного одобрения.

## Критерии готовности кандидата

1. Точный `POST /user/list` body проверен через mock transport, включая 9006, `onlyActive`, ограниченные fields и offset.
2. API errors сохраняют текущую обработку; недопустимые вводы отклоняются до сети.
3. Пагинация отмечает полную страницу как потенциально неполную; документация требует дочитать страницы до выбора.
4. Local smoke показывает 59 tools; прежние 58 имён не меняются.
5. Официальный Swagger содержит `POST /user/list`; все локальные проверки подтверждены выводом команд.
6. Один live create/readback после явного GO подтверждает задачу ровно одним write; заголовок, исполнитель, смысловое описание и срок-date-only проверены.
7. Сравнение с официальным MCP ограничено наблюдаемым lookup/confirmation UX; выводов о победителе или скорости нет.
